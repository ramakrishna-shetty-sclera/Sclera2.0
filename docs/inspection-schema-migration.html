Monolith → Microservices: Schema & Legacy Data Migration

How the single-tenant VDMS edge server (Java/Hibernate/MySQL monolith) maps onto the Sclera 2.0 application-plane services (Spring Boot/Postgres, schema-per-tenant), how we move the old data safely, and why the new schema is structurally better and more scalable.

Companion to the Inspection Module overview · full design committed at docs/inspection-schema-migration.md

1 The monolith we're leaving — what the legacy schema actually does

The edge server keeps two parallel trees with identical shape: a template tree, and a full clone of that tree for every single filled checklist. Answers live embedded inside the cloned rows — there is no answers table.

TEMPLATE (design time)                     INSTANCE (runtime — CLONED PER RUN)
global_checklist                           record_checklist          (status, result live here)
└─ global_checklist_items                  └─ record_checklist_items    (item.value / item.result = the answer)
   └─ global_checklist_options                └─ record_checklist_options (selected 0/1, value)
      └─ recursion: item.option_id             └─ same recursion via record option id
         = conditional child question             (unbounded depth in schema, 1–2 in practice)

Legacy characteristics that shape everything

  • Row explosion: every run copies the entire item + option tree, answered or not
  • Answers embedded in the clone — reporting means walking trees, not scanning a flat table
  • Recursion through options: a child question hangs off the option that reveals it
  • String PKs, epoch-millis BigInteger timestamps, is_removed soft deletes everywhere
  • No tenant column at all — each edge box is one customer; scaling = another server to babysit
  • One shared MySQL: config, templates, runs, work orders, history all coupled in one deploy unit

2 Ownership split — every legacy table gets exactly one new owner

The decomposition rule: templates are authored → procedure-service; runs and lifecycle → inspection-service; physical targets → helper-service (future asset/location services). Across services we store ID + denormalized name, never a DB foreign key.

Legacy table (monolith)New ownerNew concept
global_checklist (+items, +options)procedure-svcProcedure template with item tree (parent_option_id preserves conditional questions 1:1)
global_inspection_recordinspection-svcinspection_config — name/code/assignees/frequency/schedule days + toggles
global_inspection_relation (+assignees)inspection-svcTagging: tagged_procedure + procedure_target (association_type 1→ASSET, 2→LOCATION, 0/3→untargeted)
global_checklist_conditionsinspection-svcOuter conditions (email alert / work-order triggers)

3 The key design change: stop cloning the tree

Templates stay relational in procedure-service (they're edited). Instances become one immutable JSONB snapshot + flat answer rows in inspection-service (they're filled and reported on).

Monolith — clone per run

record_checklist tree clone

  • (items + options) × every run — millions of rows that are 95% duplicate template data
  • Answers buried in cloned item/option rows — analytics requires recursive tree walks
  • Recursive SQL on the hot fill/read path
  • Template ↔ instance drift handled by brute-force copying
  • Failed/pass reporting = string compare inside the tree
→
Microservice — snapshot + flat answers

checklist + checklist_answer

  • 1 JSONB snapshot per run + rows only for questions actually answered — orders of magnitude fewer rows
  • checklist_answer is flat & indexed (item_id, failed, result) — ESG/reporting is a plain scan
  • Conditional questions evaluated client-side from the snapshot — zero recursive SQL at runtime
  • Snapshot is immutable: what the filler saw can never drift; template edits never corrupt in-flight runs
  • Typed value JSONB + selected_option_ids UUID[], real TIMESTAMPTZ, real UUIDs
Why this matters: the monolith paid for immutability by cloning entire trees; we get the same guarantee from one snapshot column — cheaper to store, trivial to serve, and it decouples inspection-service from procedure-service at runtime (a procedure-service outage cannot block anyone filling a checklist).

4 Migrating the old data — ordered, idempotent, per-tenant ETL

One edge deployment = one tenant = one target Postgres schema. Order matters because of cross-service ID mapping. Reads come from a MySQL replica; the migrator runs per tenant, in parallel, with zero cross-talk.

Provision the tenant

Insert into tenant_registry → CREATE SCHEMA t_<org> → run tenant Flyway. migration_map lives inside the tenant schema, so re-runs are self-contained.

Locations + devices → helper/asset services

legacy string PK → new UUID, recorded in migration_map for FK rewiring

Template trees → procedure-service

global_checklist(+items,+options) → template + checklist_item + checklist_item_option (walk the recursion, keep parent_option_id)

Configs → inspection_config

global_inspection_record → epoch-millis → timestamptz, frequency string → enum, toggles mapped 1:1

Tagging + conditions

global_inspection_relation → tagged_procedure + procedure_target; global_checklist_conditions → outer_condition

Filled runs → checklist + checklist_answer

Serialize each record's OWN tree into procedure_snapshot (never re-point at the migrated template — per-record trees may have diverged; the record's tree is the truth). Extract answers: item value/result → answer rows, selected options → selected_option_ids. Map statuses (todo/in_progress/completed/exception/incomplete_expired → new enum).

History + work orders

record_checklist_history → checklist_history; workorder → checklist_work_order (external WO id kept opaque)

Validate

Per-table counts (minus is_removed), checksum of status/result distributions, random-N deep compare (legacy tree vs snapshot+answers rendered back), referential sweep (every target resolves in asset/location service).

Cutover

Historical load is repeatable → short freeze → delta pull via sync_timestamp → edge server read-only → final delta → clients switch to the gateway APIs.

🔑 ID strategy

  • Mint new UUIDs everywhere
  • legacy_id column kept on every migrated row (provenance)
  • migration_map(entity, legacy_id, new_id) → idempotent upsert; safe re-runs

🧹 Data hygiene

  • is_removed=1 rows are not migrated (archive schema if audit needs them)
  • Epoch-millis BigIntegers → TIMESTAMPTZ
  • Failed-vs-complete decided once at mapping time (result column, status derived)

⚙️ Tooling

  • One-off Spring Batch / plain-JDBC migrator per service
  • Reads the MySQL replica, writes with search_path pinned to the tenant schema
  • Tenants migrate in parallel — each is an independent unit of work

5 Why the microservice schema beats the monolith — and how it scales

Not decomposition for its own sake — each advantage below is something the monolith structurally cannot do.

🏢 Real multi-tenancy scale

  • Monolith: one server per customer, no tenant column at all
  • New: schema-per-tenant Postgres — one fleet serves every org; JWT org_id routes to the schema at connection time
  • Isolation is physical (search_path), not a WHERE clause someone can forget — cross-tenant reads verified to 404
  • New tenant = registry row + auto-provisioned schema, not new hardware

📈 Independent scaling scale

  • Fill/submit traffic (checklists) scales independently of authoring (procedures) and master data (assets)
  • Stateless services behind the gateway → horizontal replicas per service, sized to their load
  • One DB per service: hot checklist writes can't starve template reads
  • Snapshot design removes the cross-service call from the fill path entirely

🚀 Independent deployability

  • Each service has its own Flyway lineage — schema changes ship per service, per tenant, without a monolith release train
  • A failed tenant migration suspends that tenant, not the fleet
  • Blast radius of a bad deploy = one service, not the whole product

📊 Reporting & ESG

  • Flat, indexed checklist_answer replaces recursive tree walks
  • Pass/fail/percentage queries become single-table scans
  • Kafka InspectionCompletedEvent feeds warehouses/CMMS without touching our DB

💾 Storage & performance

  • Orders-of-magnitude fewer rows: 1 snapshot + answered-only rows vs full tree clone × every run
  • No recursive SQL on hot paths; runtime rendering is client-side from the snapshot
  • Proper types (UUID, TIMESTAMPTZ, JSONB, arrays) instead of string PKs and epoch BigIntegers

🔒 Clear contracts & safety

  • Each dataset has exactly one owner; integration is API + events, never shared tables
  • No cross-service DB foreign keys → services evolve schemas without lockstep coordination
  • Immutable snapshots make audit history tamper-evident by construction
  • Fine-grained authz (OpenFGA) and HMAC internal calls — the monolith had none of this
Honest trade-offs we manage: cross-tenant reporting becomes a deliberate act (warehouse export / UNION views) — which is also the isolation win; connection-pool search_path hygiene must be engineered (reset on release; session pooling if PgBouncer); schema-per-tenant is comfortable to low-thousands of tenants per database — far beyond edge-migrated counts, revisited only if tenant count explodes.
One-line summary for the meeting: we keep templates relational where they're edited, snapshot them where they're filled, and split ownership so each service scales and deploys alone. Legacy data moves per-tenant through an idempotent, validated ETL with legacy_id provenance and a delta-based cutover — no big-bang, re-runnable at any point, and every tenant lands in its own isolated schema.
