Inspection Module — Features & Service Ownership

Digital inspection of building assets (IT + OT) for compliance. Property, facility and security teams configure recurring inspections over procedures tagged to assets and locations, fill checklists (including via QR scan), and track everything through a task dashboard and map views.

Prepared for the microservices sync · owners of sclera-inspection-service (+ procedure & helper services)

1 Where we sit — service landscape

2 Main features (all live, gateway-fronted, E2E verified)

The full KT feature set for the Inspection module is implemented and Postgres-persisted. Card colour = owning service.

📋 Procedures (checklist templates) procedure-svc

A Procedure is a reusable checklist: sections containing typed questions (boolean, single/multi-choice, text, number), each with required flag and options.

  • Author → Publish → Archive lifecycle with versioning
  • Published templates are what tagging and checklists snapshot from
  • Publish emits a Kafka event; snapshots served internally over Dapr (HMAC-signed)
GET/POST /api/v1/question-templates  ·  POST …/{id}/publish

🏢 Locations & Assets helper-svc

The physical targets of inspection. Locations form a building → floor → location hierarchy; assets (IP / NON-IP) live at locations.

  • Full CRUD, tree UI for locations, filterable asset list
  • Every asset/location row can open the Tagged-Procedures modal (tag & fill in place)
  • Persisted schema-per-tenant like the rest of the plane
/api/v1/helper/locations  ·  /api/v1/helper/assets

⚙️ Inspection Configuration inspection-svc

The recurring-inspection definition: who inspects what, how often, under which rules.

  • Name, unique Code (422 on duplicate), description, category, priority
  • Primary + secondary assignee (must differ — validated)
  • Frequency + schedule days (Mon–Sun)
  • Toggles: Bypass Scan, Check-in/out, Enable Points, Merged View
GET/POST/PUT/DELETE /api/v1/inspection-configs

🔗 Procedure Tagging inspection-svc

Associates procedures with assets/locations inside a config. Each procedure × target combo carries its own condition and assignee.

  • Tagged procedures + targets (ASSET | LOCATION) as sub-resources of a config
  • Outer conditions on the whole inspection → email alert / auto work-order
  • Single GET returns the whole tagging tree; deleting a config clears it
/api/v1/inspection-configs/{id}/tagged-procedures | targets | conditions | tagging

✅ Checklist Lifecycle inspection-svc

Generate one checklist per tagged-procedure × target; fill against the live template; every action appends to an audit history.

  • Check-in gate (422 if required and skipped), save vs save-and-checkout
  • Submit: any failed answer ⇒ whole checklist FAILED
  • Exception (with reason), mark-incomplete, reopen, reassign, work orders
  • Answers stored per question; procedure snapshot preserved
POST /api/v1/checklists/generate  ·  …/{id}/check-in | answers | submit | exception | reopen | work-order

📱 Reactive Service (QR) inspection-svc

On-demand inspection: associate a procedure to a location, print the QR, scan to raise a request.

  • Create mints an opaque QR token; QR rendered + downloadable in UI
  • Scan resolves org-scoped; raise request = assignee + due date
  • Produces a checklist (source = REACTIVE_SERVICE) that flows through the same lifecycle, dashboard and map automatically
  • Deep-link survives the login redirect
/api/v1/reactive-services  ·  GET …/by-token/{token}  ·  POST …/{id}/requests

🏷️ Tagged Procedures (standalone) inspection-svc

Tag a procedure directly to an asset/location outside any config — both KT modes implemented exactly.

  • Reusable template: persistent link, each Fill spawns a fresh checklist, link stays in To-Do forever
  • One-time: creates a single checklist directly, nothing remains after completion
  • Default assignee = the caller's JWT email; duplicate tag → 422
/api/v1/tagged-procedures  ·  POST …/{id}/fill  ·  POST …/one-time

📊 Task Dashboard & Maps inspection-svc + SPA

Every checklist from every source in one operational view, fillable inline.

  • Stat row (incl. overdue), search, filters: status, source (Inspection / Reactive / Tagged / Scheduled), inspection
  • Row click → inline fill modal (shared fill panel component)
  • Task Map: building → floor → location spatial view with status-coloured checklist markers, roll-up counts, fill-in-place
  • Covers both KT "Task Map" and "Inspection Map" requirements
GET /api/v1/checklists?status=&source=&configId=

3 Checklist status model (the contract other teams see)

TO-DO → check-in → fill → submit → COMPLETE / FAILED
side states: EXCEPTION (issue raised while filling, with reason) INCOMPLETE (missed due date) — both can reopen → TO-DO, logged in history
Any single failed answer fails the entire checklist
Check-in required (if enabled on the config) before save/submit — else 422
Finalized checklists cannot be edited
Every transition appends an immutable history entry
Work orders can be raised manually per checklist
Assignee resolution: target assignee → config assignee → caller

4 Integration contracts we publish & consume

ContractDirectionDetail
REST APIInbound All routes versioned under /api/v1/**, reached only via the gateway. Uniform response envelope {success, data, pagination, error, meta} with correlation IDs.
Template snapshotInternal (Dapr) inspection-service → procedure-service service-invocation, HMAC-signed. Checklists snapshot the template at generation time — template edits never mutate in-flight checklists.
Kafka eventsBoth Consume: template published/updated. Produce: InspectionCompletedEvent — downstream teams (CMMS, ESG, reporting) can subscribe without touching our DB.
AuthN / AuthZInbound JWT (multi-realm Keycloak) with org_id / org_type claims; OpenFGA org checks on top (fail-closed). Internal endpoints HMAC-only, wrapped in tenant context.
TenancyCross-cutting Schema-per-tenant Postgres. First request from a new org auto-provisions its schema + runs tenant Flyway migrations. No org_id columns leak into queries — isolation is physical.

5 Our responsibilities as service owners

What the rest of the org can hold us accountable for — and what we hold ourselves to.

🧭 API & data ownership

  • Sole owners of the inspection data model: configs, tagging, checklists, reactive services, tagged-procedure links
  • Backward-compatible, versioned REST contracts; breaking changes only via a new version
  • Validation at the boundary (unique code 422, assignee rules 400, dup-tag 422)
  • No other service reads our tables — integration is API + events only

🔒 Security & tenancy

  • Every endpoint authenticated (JWT) and org-scoped; OpenFGA checks fail closed
  • Internal endpoints HMAC-signed, never exposed through the gateway
  • Tenant isolation is schema-level; we own tenant provisioning + per-tenant migrations
  • Cross-tenant access verified to 404 (tested with a second org)

📡 Events & integrations

  • We publish InspectionCompletedEvent — schema stability is on us
  • We tolerate procedure-service unavailability gracefully (snapshot at generate-time, not fill-time)
  • Consumer-group hygiene on template events; idempotent handling

🩺 Operability

  • Liveness/readiness on /actuator/health/readiness per service
  • Flyway-managed schema — no manual DDL, repeatable from zero
  • Run scripts + docker-compose profile for full local bring-up; documented cold-start
  • Audit history on every checklist action for supportability

🧪 Quality

  • E2E verified through the gateway for every feature: config → tag → generate → fill → submit, QR scan flow, both tagged-procedure modes
  • Persistence proven across full service restarts
  • Lifecycle guards tested (check-in gate, finalized immutability)

🗺️ Roadmap items we own

  • Legacy ETL from the VDMS edge server (design doc committed: docs/inspection-schema-migration.md)
  • FGA tuple backfill for pre-FGA objects
  • Scheduled generation (frequency/schedule-days currently config-only — cron generation is next)
  • Work-order handoff to CMMS once its API lands
