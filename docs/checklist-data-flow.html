1 Architecture at a glance

The React SPA never talks to the inspection service directly — every call goes through the gateway (session cookie + CSRF header), which forwards it with the org/user identity. The inspection service stores its data schema-per-tenant in PostgreSQL. Checklist questions are not stored by the inspection service — they are rendered live from the procedure template, fetched from sclera-procedure-service. Only answers (keyed by questionId) are stored with the checklist.

2 Configuration data stored in the database

An inspection is configured in two parts: the inspection config (the VDMS "create inspection" form — who, when, which options) and the tagging aggregate (which procedures the inspection runs, on which assets/locations, plus inspection-wide alert conditions). All rows live in the tenant's schema; org_id is kept as a defense-in-depth cross-check.

4 What the checklist looks like on the UI

Route /checklists/:id → ChecklistFillPage → ChecklistFillPanel. On mount it loads the checklist (GET /api/v1/checklists/{id}), then the question template (getTemplate(procedureId)), and hydrates a local draft map { questionId → { value, failed, comment } } from the stored answers. Question types: TEXT · NUMBER · BOOLEAN · SINGLE_CHOICE · MULTI_CHOICE · DATE · PHOTO · SIGNATURE.

5 Backend data flow — saving checklist answers

What happens end-to-end when the user clicks Just save / Save & checkout / Submit.

1
Frontend · ChecklistFillPanel
collect() builds the payload from drafts

Every drafted question becomes { questionId, value: JSON.stringify(value), failed, comment }. Values are always JSON-stringified — a multi-choice answer is stored as "[\"A\",\"B\"]", a number as "6.2". On reload, parseValue() JSON-parses them back.

2
Frontend · api/checklists.ts
HTTP call through the gateway

Save: PUT /api/v1/checklists/{id}/answers body { answers, checkout: false|true }.
Submit: POST /api/v1/checklists/{id}/submit body { answers, checkout: true }.

3
Gateway (BFF)
Session + CSRF, then forward with identity

Validates the session cookie and CSRF header, resolves the user's org, and forwards the request to sclera-inspection-service with the authenticated principal. A tenant filter maps the org to its PostgreSQL schema (TenantContext → schema-per-tenant connection).

4
ChecklistController
Authorization gate

@PreAuthorize("@fga.checkOrg('can_manage_inspections')") — an OpenFGA check that the caller may manage inspections in this org. @Valid enforces DTO limits (value ≤ 8000 chars, comment ≤ 2000, questionId required).

5
ChecklistService.saveAnswers() — @Transactional
Business-rule guards, then replace answers

Guards: ① getOwned — must exist for this org (404 otherwise). ② requireFillable — COMPLETE/FAILED are finalized; INCOMPLETE/EXCEPTION must be reopened first. ③ requireCheckedInIfNeeded — if check_in_required and no check_in_at → "Check in before filling".

applyAnswers: answers.clear() then re-add each input — a full replace, not a merge (that's why the answer table has no unique question key). Then a history line is appended: SAVE or SAVE_AND_CHECKOUT (which also sets check_out_at), and updated_at is bumped.

6
PostgreSQL (tenant schema)
One transaction commits everything

UPDATE checklist … · DELETE/INSERT checklist_answer … (collection replace) · INSERT checklist_history …. All-or-nothing: a guard failure rolls back with a 4xx business error.

7
Response → Frontend
Full ChecklistResponse comes back; UI re-hydrates

The service maps the saved entity to ChecklistResponse (answers + history + work orders included). The panel calls hydrate() — state, drafts and the history card refresh from the server truth, and a "Saved." notice is shown.

Submit differs in one step

On POST /{id}/submit, after the same guards and optional applyAnswers:

boolean anyFailed = c.getAnswers().stream().anyMatch(Answer::isFailed);
c.setStatus(anyFailed ? FAILED : COMPLETE);
if (c.getCheckOutAt() == null) c.setCheckOutAt(now);
c.log("SUBMIT", "Marked " + c.getStatus(), now);

One answer with failed = true fails the entire checklist. Checkout is stamped if it wasn't already, and the checklist becomes read-only (finalized).

7 Checklist status lifecycle

TODO— save / save&checkout keep it here — submit →COMPLETE orFAILED(any answer failed)
TODOadd-to-exception →EXCEPTION reopen →TODO
TODOmark-incomplete (overdue) →INCOMPLETE reopen →TODO
  • COMPLETE / FAILED are terminal — every mutating endpoint rejects them ("already finalized").
  • EXCEPTION / INCOMPLETE cannot be filled directly — they must be reopened to To-Do first.
  • Assignee updates and work-order creation are allowed in any state and are history-logged.
